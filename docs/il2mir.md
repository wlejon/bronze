# il2mir: bronze IL to brass MIR

## 1. Overview
`src/codegen-brass/il2mir/` lowers bronze's IL to brass MIR. It lives in bronze, and brass knows nothing about it. The pipeline is `bronze::il::Module` → `il_to_brass_ast` (`codegen-brass/il_to_brass_ast.*`) → `il2mir::BronzeModuleAST` → `il2mir::translate_bronze_ast` → `brass::Module`. `BrassBackend` then runs that module through brass's pass pipeline (`il2mir::pass_pipeline_options`) for AOT objects, the JIT, or the tiered engine.

Everything is in the top-level namespace `il2mir`, which pulls in `brass` (`il_ast.h`). The value/TLS/IC layout constants come from the bronze ABI header (`il_abi.h`), not from copies.

The lowered code calls the bronze runtime (`bronze_*`, `brass_gc_*`) by name. Brass resolves those names through its generic host-symbol hook, `brass/runtime/host_symbols.hpp`. `codegen-brass/brass_symbol_registration.cpp` installs a `HostSymbolProvider` that binds the real bronze ABI (the `BRONZE_ABI_FUNCTIONS` X-macro), and the math and parallel helpers into every engine a brass tier creates: the fast interpreter, the baseline JIT, the tier-2 installer JIT, deopt and the reference interpreter.

Bronze's objects live on brass's collector. Each thread's `bronze::Heap` (`runtime/heap.h`) owns one `brass::gc::Heap` and binds it as the thread's current heap, so every object bronze-run code creates (objects, arrays, environments, closures, strings, and the brass coroutine frames of suspended generators and async functions) is a brass heap object whose payload begins with bronze's `HeapObjectHeader`. Bronze registers the object layouts and trace functions (`runtime/heap_trace.cpp`), and the brass interpreters on the thread register their frames with that same heap. The inline allocation paths (`il_alloc_lowering.cpp`) bump the thread's TLS allocation window, which is bound as the brass heap's allocation buffer, and write brass's cell header (`gc_cell_header` in the TLS block) in front of each bronze header. Bronze's `brass_gc_write_barrier` (`runtime/gc.cpp`) is the process's only definition of that name: it strips the NaN-box tag from the object operand and takes brass's card barrier on whichever of the thread's heaps holds the object, overriding brass's `brass_default_gc_write_barrier` through the symbol table.

Compiled code roots its JS values through brass stack maps, not through anything bronze keeps. A `Dynamic` value crosses every compiled-function boundary as MIR `tagged` (`lower_abi_type`): SSA results, block params, and the params and returns of functions with a body. Native imports keep raw `i64` signatures. Arithmetic, tag tests and runtime calls work on `i64`, so every use unboxes with `bitcast.i64.tagged` (`get_val_by_id`) and every result boxes back with `bitcast.tagged.i64` (`set_inst_result`). `unbox_tagged` folds a box that sits in the same block with no call or safepoint between it and the use, and `ensure_type` folds `box(unbox(x))`, so straight-line code keeps its values in registers. Brass records every tagged value live at a safepoint, in a register, a spill slot or an interpreter register, as a stack-map root whose `value` kind is `Tagged`. The collector updates it in place and keeps its NaN-box tag. Arguments passed through memory (a construct, a method call, a super call, or a dynamic call with more than 16 arguments) go through one `alloca.tagged` argv block per function, sized to the widest such call. The block is zeroed, and each of its words is a root at every safepoint. A value is a root only while it is live. A native call hands the native raw pointers into a handle's data or a typed array's bytes, so it ends with `keep.alive` (lowered to MIR `keep_alive`) over those owners, placed after the result has been wrapped or copied: a collection inside the native, inside a program the native re-enters, or inside the result's conversion cannot run a handle's destructor under the native. AOT objects carry each function's encoded stack map in their `bronze_code_range` table, and `bronze_register_code_ranges` hands those maps to brass's code registry when the image loads. A collection triggered from C++ (bronze's allocator, a builtin) walks the native stack from where it is (`HeapConfig::walk_stack_on_host_collection`). C++ frames root their own values with `Rooted<>`, `RootedArgs` and `RootedBlock` on the runtime's C++ shadow stack. The walk steps through the C++ frames between two compiled frames by their unwind information (brass's `native_unwind.hpp` off Windows), so neither the runtime nor a host has to keep frame pointers.

There is no textual IL front door and no mock runtime. The only input is the IL bronze's compiler builds in memory.

## 4. Impedance Mismatches Identified & Resolved

1. **Dynamic Call Edge (`name.resolve "print"` + `call.dynamic`)**:
   - *Issue*: Bronze compiles JavaScript `print(...)` into a dynamic global name lookup (`name.resolve "print"`) followed by a variable-argument `call.dynamic` rather than a static opcode.
   - *Resolution*: Lowered to host symbol descriptors and dynamic dispatchers that unpack NaN-boxed argument payloads and format output identically to Node.js.
2. **ECMA-262 Number Formatting**:
   - *Issue*: C/C++ default `%g` or `%f` prints integer doubles as `1.62412e+06` or `55.0`.
   - *Resolution*: Implemented `std::to_chars`-backed JS-style formatting where integer-valued floats print without exponents or trailing decimals, matching Node.js `ToString(Number)` byte-for-byte.
3. **Lexical Scope & Per-Iteration Capture**:
   - *Issue*: Closures capture mutable outer scopes (including per-iteration variables in `for (let i...)` loops).
   - *Resolution*: Lowered to `BronzeEnv` frame chains and `BronzeClosure` handles passing the environment context as hidden first argument.

## 5. Exceptions

A JS throw is a brass raise; nothing stores a pending exception for a caller to test, and code that does not catch pays nothing on its normal path (`il_lowering_eh.cpp`):

- A `throw` inside a `try` is a branch to its handler with the value. One outside a `try` is a MIR `throw`, which leaves the function.
- A call inside a `try` is a MIR `invoke`. Its unwind edge goes to one `landing_pad` per handler, which receives the thrown value in the return register and branches to the handler with it. A call outside a `try` is a plain call with nothing after it.
- `exc.take` reads the value the handler was given.

The value crosses C++ as exactly one type: `brass::runtime::BrassException` (`runtime/exception.h`). The runtime raises with the `[[noreturn]]` `rtThrow*` helpers, which throw one; a host native or sibling `_api` function throws one the same way. The C++ frames between the raise and the nearest compiled `invoke` unwind as they do for any C++ exception, `Rooted<>` destructors included. brass's personality routine then lands the exception at the pad: `brass_seh_personality` on Windows, named by every compiled function's `.xdata`; `brass_sysv_personality` elsewhere, named by the `.eh_frame` CIE of every compiled function with pads, which finds the pad in the function's LSDA or brass's JIT registry. A raise from compiled code (MIR `throw`) whose pad is in a compiled caller is found by brass's frame walk and jumped to directly. Every tier lands at the same pads: the interpreters' `invoke` catches the C++ exception, and tier-up, OSR and deopt keep the handler blocks.

C++ that calls compiled code, or catches for a reason of its own, uses `rtTryCatch(body, thrown)`: it runs `body` and answers whether it threw, storing the value in `thrown` after the handler has returned, so a collection during the body cannot leave it stale.

At the embed boundary (`embed.h`) an entry point that returns a result reports a throw in it: `call`, `construct`, `parseJson` and the property getters return a `CallResult` whose `thrown` is set, and `catchThrow(body)` does the same for any host code that calls into JS. `setElement` drops the write when a setter throws. `deleteProperty` and `createTypedArray` let the exception propagate to the host. An uncaught throw at the top of a module leaves `rtRunModuleEntry`, which reports it with its stack and exits the process with status 1; `BrassTieredProgram::run` lets it leave as the `BrassException` it is. A promise job's throw rejects its promise, and an unhandled rejection is reported when the job queue drains.

`Error.prototype.stack` and `Error.captureStackTrace` walk the native stack by its unwind information when the error is made (`runtime/stack_trace.cpp`), so a stack reads the same whether the error is thrown, caught or never thrown.

## 6. Generators and async functions

Generators, async functions, async generators and a top level that awaits are brass coroutines at every tier (`lower/lower_generator.cpp`, `il_lowering_coro.cpp`, `runtime/coro.cpp`).

- **One body, suspensions in the middle.** src/lower lowers such a function as an ordinary body in which each `yield` / `await` is `%sent = coro.suspend <kind> %v` followed by `coro.mode`, and a branch on the mode: next continues with `%sent`, throw is a `throw %sent` at that point, return is a `return %sent` at that point. `throw()` and `return()` therefore reach the enclosing `catch` and `finally` blocks through the same lowering as any other throw or return, and bindings stay in SSA. `yield*` is a loop around `iter.delegate` (`runtime/iterator_delegate.cpp`), which steps the inner iterator with the resumption's mode.
- **Stub and body.** `splitCoroutineBody` moves the blocks into `<name>.body` (coroKind set) and leaves `<name>` as the stub `coro.start <kind> @<name>.body(params)`. il2mir lowers the stub to MIR `coro_create` (whose frame allocation is a GC point, so its tagged arguments are roots across it) and `bronze_coro_start(kind, frame)`, which answers the generator object or the promise. The body takes the frame as a leading `gcref` parameter.
- **Suspension.** `coro.suspend` is MIR `coro_suspend` with a state id whose low two bits are the kind (`BRONZE_ABI_SUSPEND_KIND_MASK`: start, yield, await, delegate). The resumer passes the address of a rooted cell holding the sent value as the resume value, and the body loads it after the suspend, so the value is current however much the resumer allocated. `coro.mode` is MIR `coro_resume_mode`. A body is resumed from C++, which does not carry the pinned TLS register, so the body fetches the block (`bronze_tls_block_addr`) at entry and after every suspend.
- **Frame lowering.** il2mir runs `brass::lower_coroutines` on the module before its optimization pipeline: until the split, a suspend is an ordinary instruction to the passes, which would move a frame read or an unboxed reference across it. The lowering spills every value live across a suspend into the frame and records the frame layout on the body; allocas must be in the entry block. AOT bodies allocate their frames through `brass_coro_create` (a `BRONZE_ABI_BRASS_SYMBOLS` entry: the shared runtime exports it as an alias of brass's `brass_default_coro_create`, the one definition of the name in the process even when the host links brass statically); JIT tiers through the body's CoroBody descriptor. A tier-0 body resumed with no interpreter running starts one through the program's pipeline.
- **Ownership.** A new frame is one of brass's roots until `bronze_coro_start` hands it to its owner (the generator object, the async function's machine, the async generator), which `rtCoroAdopt` unroots; from then on the owner traces it. The heap is bound on the thread's first entry into generated code (`bronze_tls_enter`), before any frame can be created.
- **Drivers.** The runtime keeps the protocol state: `builtin_generator.cpp` (27.5.3), `builtin_async.cpp` (27.7.5) and `builtin_async_generator.cpp` (27.6.3) resume through `rtCoroResume` and subscribe awaits through `rtCoroAwait`, which subscribes the awaited promise itself when it is one (one reaction job per await).
- **Not yet:** async stack traces (the brass awaiter links are not set, so a stack captured in a resumed body ends at the body's frame), and leaving a for-await loop early does not await the iterator's `return()` result (`tests/oracle/cases/blocked/for_await_close_awaits_return.js`).

## 7. Speculation sites

Under the tiered pipeline (`brass_tiered_engine.cpp`, every tier except standalone `--tier=2`), a program is lowered with a `SpecFeedback` (`il2mir/il_speculation.h`). The program owns it because the lowered code increments its counters in place. Each inline fast path whose test can fail at run time is a **site**: `br_if %hit, fast, slow`, where `slow` counts the miss and then calls the generic helper.

| Site | Fast path | Slow path | Armed when |
|------|-----------|-----------|------------|
| dynamic `+ - * /` (`il_lowering_ops.cpp`) | both operands Numbers: f64 op, NaN-canonicalized box | `bronze_dynamic_*` | not by default (`BRONZE_SPEC_ARM_KINDS`); with bit 1 set, the slow path never ran |
| `prop.get` (`lower_prop_get_mono`) | plain object whose shape is the site's way 0, own data slot, inline or overflow | the poly scan below | at most 2 misses (the cold IC fills) |
| `prop.get` poly scan (`other_ways_hit`, kind `PolyProperty`) | on a way-0 miss with way 1 filled (an empty way 1 goes straight to the helper), the receiver's shape against ways 1..3 (straight-line selects), own data slot of the matching way | `bronze_prop_get` | at most 8 misses (fills of up to 4 shapes); a megamorphic site keeps its branch |
| `prop.set` (`lower_prop_set_mono`) | the same test, then store plus write barrier for a reference | `bronze_prop_set` | at most 2 misses |
| `method.call` of `sqrt`/`abs`/`floor`/`ceil`/`sin`/`cos`, one argument (`lower_builtin_method_call`, `il_lowering_calls.cpp`), and a one-argument `call.dynamic` whose callee a `prop.get` of one of those keys made (`const cos = Math.cos; cos(x)`) | the method, read by the inline `prop.get` path (its own site), is a function object whose code pointer is the `bronze_math_*` builtin's, and the argument is a Number: the machine op (sin and cos: a direct call of `bronze_math_sin_f64` / `bronze_math_cos_f64`, the kernel the builtin runs), NaN-canonicalized box | `bronze_call_dynamic_1` on the method already read | the slow path never ran |
| `method.call` with a `directTarget` (`lower_direct_method_call`, kind `Property`, tag `()key`) | plain receiver whose shape a DIRECT entry of the site's method IC (way 0 or way 1) latched, with that entry's code pointer the named function's wrapper: a direct call of the named function on its typed signature, an omitted argument (whose parameter is tagged) passed as undefined | `bronze_call_method` | at most 2 misses |

The `directTarget` of a method call (`lower/direct_method_table.h`) names the nearest declaration at or above the receiver's inferred class. It is a guess: an override in a subclass (in this module or another), a patched prototype or a receiver of another class entirely resolves the key to another function, so the direct call is only ever the fast half of a site. The slow path is the generic call, which latches the IC for the receiver in hand, and the first call always takes it. Every tier's `func_addr` of a program function is its one lazy stub (brass `canonicalize_function_addresses`), so the code pointer the IC latched in Tier 0 is the one tier-2 code compares against. For the same reason loop property hoisting (`loop_prop_analysis.cpp`) does not take the named function's effects for the call's: a method call is an unresolved call there.

With feedback, every keyed get and set site gets the inline path, not only the ones inference proved monomorphic (`is_mono`). Set sites stay out-of-line while a shape census counts every write, and use way 0 only.

A read that tiered up monomorphic has its way-0 guard armed; a second shape deoptimizes it, and the reoptimized copy keeps the way-0 branch and arms the scan's guard, so a site of 2 to 4 shapes stays inline in tier-2 code and deoptimizes only when it turns megamorphic. The poly block recomputes the receiver's words from the operand rather than carrying the way-0 block's, so an armed way-0 guard's state is the operands alone (carrying them kept them materialized in tier-2 code, about 50 ms of nbody). When a front pass arms any guard of a copy it drops the pinned branches' unreachable sides (`cfg_simplify_function`, branch folding and dead blocks only) before the tier-2 passes, so inlining and GVN-PRE never walk them. `BRONZE_NO_POLY_SCAN=1` lowers a way-0 miss straight to the helper (the A/B seam).

The polymorphic sites use the site table's data ways, not brass's code patching (`patchable_const_*` / `patchable_call`, brass `docs/patching_protocol.md`). Under the tiered pipeline that facility patches one engine's code by symbol: baseline code registers no patch sites, the fast interpreter looks a patched constant up by string on every execution, and nothing fans a patch out to a function's Tier-0, Tier-1, tier-2 and OSR copies. A module's IC table is also per thread (`per_thread_module_data`) while its code is shared, so a shape patched into code would be one thread's answer in every thread's code. Shapes are immortal and non-moving, so an immediate would be GC-safe; what it would save is one L1 load per way.

**Guards.** In a function that can deoptimize, each site also has a guard in front of its branch: `guard 1, "bronze.spec"` with the site's number as resume id, `slow` as the resume target, and every value live into `slow` as its state. It is always true in Tier 0 and Tier 1. When a function tiers up, `apply_tier2_speculation` (brass's tier-2 front pass, `docs/speculation_and_deopt.md` §4b in brass) reads the counts. An armed site gets `%hit` as its guard condition and its branch pinned to `fast`, so a miss in tier-2 code deoptimizes and resumes the call in Tier 0 at `slow`. Other sites lose the guard and keep the branch. Either way the copy drops its resume points. Repeated deopts invalidate the code, and brass reoptimizes up to three times with the counts the failures added.

The call-target site is keyed by the member's name, and the guard is the code pointer, which a moving collector never changes and which any replacement (`Math.sqrt = f`, another receiver's `sqrt`) fails. The slow path calls the method the site already read, so a getter runs once either way. A speculated call stages no arguments, so it adds nothing to the function's argv block.

A function can deoptimize only if nothing its slow paths read would be wrong in the fresh Tier-0 frame a resume enters. An argv block (any method or n-ary call) is an alloca that is live into the slow paths after it; brass re-creates an alloca in a guard's state in the resuming frame, with the contents the deoptimized frame's buffer holds (brass `docs/speculation_and_deopt.md` §3), so those functions deoptimize like any other. Generator and async bodies deoptimize too. brass's coroutine lowering files a suspend's resume block in the function's resume table under the state id with its top bit set (`coro_suspend_resume_id`), so a suspend's state id (which carries the suspend kind in its low bits) never takes a guard's site number. It also completes each guard's state after lowering with what the resume target now reads: the frame, which every spill store, reload and return addresses, and the reloaded copies of values that cross a suspension. A failed guard in tier-2 code finishes that resume step in Tier 0 over the same heap frame; the next resume dispatches on the frame's state as usual, in whatever tier the body has. `tiers_44_coroutine_speculation` covers each site kind before and after a `yield` / `await`, failing after tier-up.

Seams: `BRONZE_NO_SPECULATION=1` lowers without feedback (the pre-speculation lowering). `BRONZE_SPEC_NO_GUARDS=1` keeps sites and counts but emits no guards. `BRONZE_SPEC_NO_ARM=1` emits guards and never arms them. `BRONZE_SPEC_ARM_KINDS=<mask>` arms only the kinds whose bit is set (1 arith, 2 property, 4 call target, 8 poly scan); the default is 14 (`oracle-tiers-arm-all-stress-3` uses 15). Armed arith guards measured slower than their branches (about 65 ms of nbody's 420 in bro's `cpu_work.js`) because brass's linear-scan allocator kept each guard's state live to the guard's exit block, which isel places after every other block. The state values of 35 arithmetic sites (their boxed operands among them) then held registers or spill slots through the rest of `advance` (176 spill slots against 118 unarmed). brass now counts an exit block's reads at the guard's branch (45 against 88), and armed arith is about 12 ms faster on nbody. It stays off by default for another reason. An arith site's only count is its slow path's, so a site that never ran looks monomorphic: an OSR copy of `cpu_work.js`'s top level arms the arithmetic after its loop and deoptimizes on the first string `+`, which costs the strings phase about 23 ms (47 to 70) and the total all of nbody's gain. `BRONZE_SPEC_TRACE=1` prints armed/total per tier-2 copy. `oracle-tiers-deopt-stress` and `oracle-tiers-deopt-stress-3` run the tiers suite with `BRASS_DEOPT_STRESS` at 1 and 3, and `tiers_39_speculation_deopt` exercises each site kind going polymorphic after tier-up. `tiers_40_call_speculation` changes call targets after tier-up (a patched `Math.sqrt`, another receiver, non-Number arguments) and fails guards in functions with an argv block. `tiers_41_poly_ic_transitions` takes reads, writes and method reads from one shape to 2, 4 and 8 after tier-up, and does the same in a top-level loop run by OSR code (whose entry brass retires after `deopt_threshold` failures, so the Tier-0 frame a deopt resumes in does not re-enter it at every backedge).

## 8. Speculation profiles for AOT

`il2mir/il_spec_profile.h` carries the tiered pipeline's site feedback to an AOT build. A tiered run with `BRONZE_SPEC_PROFILE_OUT=<path>` writes, at exit, every site's kind, miss count, function and tag (versioned text, format in the header). `bronze build --spec-profile <path>` lowers with it: every keyed property site gets the inline path as under the tiered pipeline, with the pinned TLS block instead of the in-process not-an-object block; a site the profile shows cold gets its slow block renamed `*_cold`, which brass's block layout sinks to the end of the function; and a poly scan the profile shows megamorphic is lowered with a false hit, so a way-0 miss goes straight to the helper. Nothing is a guard: AOT has no Tier 0 to resume in, so every slow path stays a branch and a wrong profile costs layout, never correctness.

A site is named by (function, kind, tag, occurrence), the entry function as `<entry>`: the JIT and AOT lowerings of one program differ in places (inference, the eval wrapper, the Math call-target sites, which need this process's builtin address and are not lowered in AOT), and a site the profile does not name lowers as without one. Measured on bro's `cpu_work.js` built AOT: nbody 515 ms without a profile, 250 with, and 245 with an empty profile, so the win is the inline layout the profile turns on; the counts' layout adds nothing measurable there. `oracle-spec-profile` builds `tiers_39`..`tiers_41` with the profile their own tiered run wrote and holds the programs to the pinned bytes.

## 9. Calls that enter compiled code directly

In an image build (an executable, `--emit-obj`, a shared module, an AOT module image: `BrassBackend::setDirectJsCalls`), a call from compiled code to a compiled callee enters the callee's code itself instead of going through `bronze_dynamic_call` / `bronze_call_method` / `bronze_construct` and `rtEnterJs` (`il2mir/il_lowering_direct.cpp`). What the runtime path does and why skipping it is unobservable for the functions that allow it is stated once, at `BRONZE_ABI_FN_FLAG_DIRECT_CALL` (`abi/bronze_abi.h`); the flag is set from one predicate, `il::functionEntersDirectly` (no `new.target`, no `super()`, not a generator or async function).

| Site | Direct form | Otherwise |
|------|-------------|-----------|
| `call.dynamic` (`lower_closure_call`) | the callee is a function object whose flags word has DIRECT_CALL set, CLASS_CTOR clear and the current realm in its realm bytes (one load, compared against `bronze_tls_block.realm_slot`): `call_indirect` of its code with its env | `bronze_dynamic_call` |
| `method.call` (`lower_method_call_ic`) | a call of the module's one stub, `__bronze_method_call_ic`, which reads the site's IC: a DIRECT entry of either way whose latch recorded `BRONZE_ABI_METHOD_IC_DIRECT_ENTRY_BIT`, a SLOT entry whose slot holds a function passing the call test above, or an Array's EXOTIC entry under its box guard | `bronze_call_method`, from the stub |
| `construct` (`lower_construct_direct`) | a constructor whose vet byte says `bronze_construct`'s plain path has run for it, with DIRECT_CALL and the realm: the instance bumped inline, the code entered with it, the result the constructor's object if it returned one | `bronze_construct` |

The method dispatch is a stub rather than inline because it is some sixty instructions: inline at every site it cost instanced_mesh_churn 40% more build time. Being a direct call it is also an `invoke` in a block with a handler; the closure and `new` forms, whose entry is an indirect call, take the helper in such a block, and in a block that runs once. The stub has no function descriptor, so it names no frame in a stack trace. JIT code never takes these forms: the tiered engine may interpret a callee or free its code.

## 10. Guarded method inlining

`recv.m(args)` whose site the direct-method table resolved to one module function (`directTarget`) is, in an image build, compiled as the callee's body at the site, behind a test of the function the call would really enter. `lower/inline_guarded.cpp` is the pass; `inlineGuardedEnabled` (`lower/inline_guarded.h`) is the one predicate that turns it on: `bronze build` and `bronze il` only, never the JIT or the tiered engine, which may interpret a callee or replace its code.

**Layer: IL.** The pass runs in `lowerModule`'s IL-to-IL block, LAST, after typed entries, and copies each callee as it is finished: its guarded regions built, and at a site the typed-entry pass pointed at an unboxed entry, that entry's body with its `f64`/`bool` parameters bound to the site's unboxed operands. Run first (as it was tried), it was a net loss: a guarded region starts at a function's entry or a loop header, so none formed across an inlined body, and a site that had a typed entry got the generic body instead, its parameters boxed and re-tested (`rtToNumber` came to 9% of `bench/instanced_mesh_churn.js`). Afterwards the typed-entry fold (`foldTypedEntry`, every rule a fact about any `box`) runs over each changed caller, since a body bound to `box.f64 %x` operands has tests and checked unboxes that answer themselves; a fold whose result fails the dominance check is dropped. The callee's instructions are copied with their own facts (a monomorphic site, a raw unbox under a dominating `is.number`, a direct edge): each is a fact about every activation of that function, and an inlined body is one activation of it, with the same receiver and arguments the call would pass. Inline-cache sites are shared with the callee's body, as `inline_small` shares them. A callee's guarded-region copies keep their fast/slow pairing under fresh region numbers, so the frame overlay still shares their slots; inside one of the caller's own copies every copied block is that copy, the pairing that is true of all of them.

**Guard: the site's method cache.** `method.ic.is %recv, <site>, @T` (T the generic function, also when its typed entry is what is copied) is true when the call site's method IC holds a DIRECT entry (way 0 or way 1) for `recv`'s shape, latched at the current prototype-mutation epoch, whose code word is T's wrapper. That is the test the site's direct edge already makes before entering T (section 9): the runtime latches a DIRECT entry only for a plain receiver whose lookup found a function this realm made that may be entered directly, and any change that could change the lookup (an own property added, a prototype edited, `setPrototypeOf`, an accessor redefined) moves the shape or the epoch. So the inlined body runs exactly when the call would have entered T with this receiver, and modules that patch prototypes are not excluded. Two closures of T differ only in their environment and home object, which an inlined callee does not read (no `needsEnv`, no `super`, no `new.target`).

**Fallback: the real call.** A miss runs the site's original `method.call`, unchanged: its own read, its own dispatch, and the latch that a later pass through the site hits. The first pass through any site takes it.

**What is inlined.** A strict function (sloppy `this` is coerced by the wrapper, which the inlined body skips) with no environment of its own, no `arguments`, no rest parameter, no `super`, no `new.target`, no generator or async body, no handler, and no `create.func` / `env.create`; its module-scope reads (`module.env.get`, then `env.get` off that) mean the same thing in any function of the module. Dynamic parameters, or a typed entry's `f64`/`bool` source parameters bound to operands of exactly those types, and a Dynamic return. Missing arguments are `undefined` (a typed entry is built for its site's argument count and reads them so too); a site passing more arguments than the method declares has no direct edge.

**Where, and how much.** Only call sites inside a loop of their function (natural loops off the back edges; a copied body's blocks are in the loop its call was in, so nested sites qualify), since a call outside every loop runs once per entry and copying a body there buys one call for its build time. The sizes count finished IL instructions: a callee of at most 250, at most three nested levels, never a function into itself or into a body that is inlining it; a caller of more than 800 takes none (what is that big is mostly cold library code, and brass's analyses grow faster than linearly), and a caller grows to at most twice its size plus 200, never past 1500. The numbers are measured, not derived: with the callee cap at 60, `Object3D.updateMatrix` came in but `Matrix4.compose` (209) did not, and `bench/instanced_mesh_churn.js` went from 65 ms to 75-81 ms, because the call left in the loop body now had every inlined value live across it and brass's allocator spilled and reloaded them around it (a backend weakness this pass works around rather than fixes). At 250 the whole loop body is call-free but for a closure call, and the benchmark measures 54.5 ms. Without the caller bounds the three.js graph built in 26 s against 17; with them 18.6.

**Stack traces: inline frames.** Each copied instruction keeps its own span and carries an inline-frame index into its function's `inlineFrames` (callee, call span, parent frame). il2mir turns the chain into brass inlined scopes (`DebugLoc::inlined_at_id`, recorded with the callee's IL name), so brass's own inliner and this one share one representation. The object writer gives each code range an inline-frame table (`bronze_inline_frame`: callee descriptor, call position, parent) and each pc entry its frame. `find_code_sites` (`runtime/stack_trace.cpp`) expands a pc into the callee frames, innermost first, then the caller at the call's position, which is what the uninlined code's frames say: `Error.stack`, uncaught traces and console.trace print the same lines. The sampler and the profiler attribute a sample to the innermost frame and count the outer ones as callers, as they did when the call was real. A scope whose callee has no descriptor (a runtime-internal MIR function brass inlined) names no frame: its pcs report the call position.

**Exceptions.** The copied blocks take the call block's handler, so a throw in the body leaves to the caller's catch or finally exactly as a throw out of the call would; the callee has no handler of its own. Stack overflow is still checked at every real function entry; an inlined level adds its frame's slots to the caller's frame, so recursion reaches the limit a few calls sooner or later, never past it.
